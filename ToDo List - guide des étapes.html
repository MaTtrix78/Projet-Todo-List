Projet PHP – ToDo List : guide des étapes

Comment utiliser ce guide

Le projet se construit en 7 étapes, dans l’ordre. Chaque étape ajoute une partie de l’application et se termine par une version qui fonctionne, envoyée sur GitHub.

Le guide ne donne pas de code : il dit quoi construire, quelles fonctionnalités (F) et quelles règles de sécurité (S) du cahier des charges sont concernées, et comment vérifier que c’est terminé. Les exemples des chapitres 6 à 8 du cours (ajout.php, connexion.php, admin.php, la fiche d’un livre) servent de modèle.

Chaque étape suit la même démarche :

  1. Lire l’objectif et les fonctionnalités concernées dans le cahier des charges.
  2. Décider où ranger chaque morceau de code, avant d’écrire : quelle page, quelle fonction, quel fichier.
  3. Construire, seul ou avec l’aide de l’IA.
  4. Vérifier chaque point de la liste « C’est terminé quand », dans le navigateur.
  5. Répondre aux questions de l’étape dans le dossier de compréhension.
  6. Envoyer la version sur GitHub, avec un commit qui décrit l’étape.

Étape 1 – Mise en place

À la fin de cette étape, le projet est sur GitHub, la base existe avec ses données de test, et une page d’accueil vide s’affiche avec le gabarit commun. Aucune fonctionnalité n’est encore visible.

Concerné : base de données, attentes techniques (démarrage commun, gabarit, connexion à la base, erreurs), Git.

À construire

  • Le dépôt GitHub public, cloné sur votre poste. Communiquez son lien dès maintenant.
  • Le schéma de la base (les 3 tables et leurs liens), puis le script SQL : création des tables et données de test.
  • La structure des dossiers : les pages à la racine du projet, un dossier pour les fichiers inclus (fonctions, connexion, gabarit), un dossier pour le CSS.
  • Le fichier de connexion à la base, sur le modèle de connexion-bdd.php (cours, 8.1). C’est le seul fichier qui crée l’objet PDO.
  • Dans ce fichier, la création de la connexion dans un try / catch (cours, 8.5) : en cas d’échec, le détail va dans le journal avec error_log(), et le visiteur voit un message neutre.
  • Le fichier de démarrage commun, inclus en haut de chaque page : il démarre la session, désactive l’affichage des erreurs (ini_set), charge le fichier de fonctions et le fichier de connexion.
  • Le gabarit commun (en-tête avec le menu, pied de page) et une première page d’accueil vide qui les inclut.
  • Un premier README.md (en Markdown, voir le cahier des charges) : le but du projet et les étapes d’installation.

C’est terminé quand

  • le script SQL, importé dans phpMyAdmin sur une base vide, crée les 3 tables et leurs données sans erreur ;
  • l’accueil s’affiche avec le gabarit commun ;
  • un mauvais mot de passe dans le fichier de connexion affiche un message neutre, et le détail de l’erreur est dans le journal des erreurs PHP (icône WampServer, menu PHP, journal des erreurs). Remettez ensuite le bon mot de passe ;

Commit : « Étape 1 : mise en place du projet ».

Étape 2 – Les comptes

À la fin de cette étape, un visiteur peut créer un compte, se connecter et se déconnecter, et les pages réservées le renvoient vers la connexion. Tout le reste de l’application en dépend : chaque liste appartient à un utilisateur.

Concerné : F1, F2, F11 ; S3, S4, S5, S7, S8.

À construire

  • Les fonctions de requêtes sur la table utilisateur : chercher un utilisateur par son identifiant, ajouter un utilisateur. Une fonction ne voit pas les variables de la page (cours, 5.4) : elle reçoit l’objet PDO en paramètre.
  • Les pages d’inscription, de connexion et de déconnexion, sur le modèle du cours (7.3).
  • La vérification des saisies de l’inscription : identifiant non vide et pas déjà pris, mot de passe d’au moins 8 caractères (strlen() donne la longueur d’une chaîne).
  • Les fonctions utilitaires : échapper un texte (htmlspecialchars), savoir qui est connecté, réserver une page (redirection puis exit), ranger un message dans la session, puis l’afficher une seule fois sur la page suivante et le retirer de la session.
  • Le menu du gabarit, qui change selon que l’utilisateur est connecté ou non.

C’est terminé quand

  • une inscription avec un identifiant déjà pris, ou un mot de passe de moins de 8 caractères, est refusée avec un message clair, et les saisies sont conservées ;
  • dans phpMyAdmin, la colonne mdp_hash contient une longue empreinte, jamais le mot de passe en clair ;
  • un identifiant inconnu et un mauvais mot de passe donnent exactement le même message ;
  • une fois connecté, le nom de l’utilisateur apparaît dans le menu ; après la déconnexion, il disparaît ;
  • une page réservée, ouverte sans être connecté, redirige vers la connexion avec un message ;
  • après une inscription réussie, actualiser la page (F5) ne crée pas un second compte.

Commit : « Étape 2 : inscription et connexion ».

Étape 3 – Lire les listes et les tâches

À la fin de cette étape, un utilisateur connecté voit ses listes et le contenu de chacune, à partir des données de test. Il ne peut encore rien modifier.

Concerné : F3, F5 (sans les filtres), F10 ; S1, S2, S5, S6.

À construire

  • Les fonctions de requêtes sur les listes et les tâches :
    • les listes d’un utilisateur, avec pour chacune son nombre de tâches et de tâches terminées (LEFT JOIN, COUNT, GROUP BY) ;
    • une liste, à partir de son identifiant et de celui de l’utilisateur connecté : la requête ne renvoie la liste que si sa colonne utilisateur_id est celle de l’utilisateur connecté (lu dans la session). Sinon, fetch() renvoie false ;
    • les tâches d’une liste.
  • Les libellés du statut et de la priorité : les valeurs autorisées et leur libellé (« En cours » pour en_cours) sont définis une seule fois, dans le fichier de fonctions (un tableau associatif, par exemple).
  • La page « Mes listes » et la page d’une liste.
  • La page « introuvable » : code 404 avec http_response_code(), comme pour la fiche d’un livre (cours, 8.3), mais avec le gabarit commun.

C’est terminé quand

  • connecté avec le premier compte de test, « Mes listes » affiche uniquement ses listes, avec le nombre de tâches et le pourcentage d’avancement de chacune ;
  • la page d’une liste affiche ses tâches, avec leur statut et leur priorité en clair (« En cours », et non en_cours) ;
  • l’identifiant d’une liste inexistante dans l’adresse affiche la page « introuvable », avec le code 404 (visible dans l’onglet Réseau de F12) ;
  • l’identifiant d’une liste du second compte de test affiche aussi la page « introuvable », et non son contenu ;
  • une tâche dont le titre contient <b>test</b> s’affiche tel quel, sans texte en gras.

Commit : « Étape 3 : consultation des listes et des tâches ».

Étape 4 – Créer, modifier, supprimer

À la fin de cette étape, l’utilisateur gère entièrement ses listes et ses tâches. C’est l’étape la plus longue : commencez par les listes, puis passez aux tâches.

Concerné : F4, F6, F7, F8, F11 ; S1, S6, S7, S8, S9.

À construire

  • Les fonctions de requêtes : ajouter, renommer et supprimer une liste ; ajouter et supprimer une tâche, changer son statut. Pour une tâche, l’appartenance se vérifie par sa liste (jointure entre tache et liste).
  • Une page par action. Chaque page vérifie que l’utilisateur est connecté, que la requête est en POST, que les saisies sont valides et que la liste ou la tâche lui appartient. Elle range ensuite un message, puis redirige (cours, 6.4).
  • Pour une priorité ou un statut reçu : on vérifie qu’elle fait partie des valeurs autorisées définies à l’étape 3 (avec isset sur le tableau des libellés, ou avec in_array).
  • Les formulaires : création et renommage d’une liste, ajout d’une tâche (avec les erreurs au-dessus du formulaire et les saisies conservées), et des boutons de suppression et de changement de statut dans la page d’une liste. Ces boutons sont de petits formulaires en POST, avec l’identifiant dans un champ caché.

C’est terminé quand

  • chaque opération fonctionne et affiche un message de confirmation ;
  • un titre vide ou une priorité inconnue (modifiée avec F12) est refusé, avec un message clair ;
  • supprimer une liste supprime aussi ses tâches (vérifiez dans phpMyAdmin) ;
  • après chaque opération, actualiser la page (F5) ne la refait pas ;
  • aucune suppression ni modification ne se déclenche en ouvrant simplement une adresse dans le navigateur ;
  • en changeant avec F12 l’identifiant caché d’un formulaire pour celui d’une tâche d’un autre utilisateur, l’opération est refusée.

Commit : un commit pour les listes, un autre pour les tâches.

Étape 5 – Filtres, recherche et tri

À la fin de cette étape, la page d’une liste permet de filtrer les tâches par statut et par priorité, de chercher dans leur titre et de les trier. Les tâches sont lues avec la requête de l’étape 3, puis filtrées et triées en PHP avec les fonctions du cours : array_filter pour filtrer, usort pour trier, match pour choisir le tri (cours, 3.4 et 4.1). Pour la recherche, str_contains($titre, $mot) renvoie true si le mot est dans le titre (includes en JavaScript).

Concerné : F5 ; S2, S8.

À construire

  • Une fonction qui reçoit les tâches et les choix (statut, priorité, mot-clé, tri), et renvoie les tâches filtrées et triées. À vous de décider dans quel fichier la ranger.
  • Dans la partie traitement de la page d’une liste : la lecture des choix dans l’adresse ($_GET), et l’appel de cette fonction.
  • Dans la partie affichage : le formulaire des filtres, en GET, qui réaffiche les choix faits.

C’est terminé quand

  • chaque filtre fonctionne seul, et tous fonctionnent ensemble ;
  • après le filtrage, le formulaire affiche encore les choix faits, y compris le mot-clé ;
  • l’adresse contient les choix (par exemple ?id=1&statut=en_cours&tri=echeance), et la recopier dans un autre onglet donne le même résultat ;
  • une recherche sans résultat affiche un message « Aucune tâche », et non un tableau vide ;
  • une valeur de tri inconnue, tapée dans l’adresse, ne provoque aucune erreur : le tri par défaut s’applique.

Commit : « Étape 5 : filtres, recherche et tri ».

Étape 6 – Tableau de bord

À la fin de cette étape, l’accueil d’un utilisateur connecté résume ses tâches en quelques chiffres, calculés par la base.

Concerné : F9 ; S1, S6.

À construire

  • Les fonctions de requêtes qui calculent les chiffres du tableau de bord avec SQL (COUNT, GROUP BY, et ORDER BY avec LIMIT pour les 5 prochaines tâches).
  • La page d’accueil d’un utilisateur connecté, avec ces chiffres. L’accueil d’un visiteur reste une simple page de présentation.

C’est terminé quand

  • les chiffres du tableau de bord correspondent à ce que vous comptez à la main dans phpMyAdmin pour un compte de test ;
  • les 5 prochaines tâches ne contiennent ni tâche terminée, ni tâche sans échéance ;

Commit : « Étape 6 : tableau de bord ».

Étape 7 – Relecture de sécurité et finalisation

À la fin de cette étape, chaque règle de sécurité a été vérifiée dans le code, le dossier de compréhension est complet, et le projet s’installe sur un autre poste en suivant le README.

Concerné : S1 à S10, Git et livrables.

À faire

  • Relire tout le code, règle par règle (S1 à S10). Pour chaque règle, notez dans le dossier l’endroit exact où elle est appliquée : le fichier, la fonction, la ligne.
  • Chercher les oublis : une requête qui colle une variable dans le SQL, une donnée affichée sans échappement, une page réservée sans vérification de la session, une action qui ne vérifie pas le propriétaire, un formulaire qui modifie la base en GET, une requête SQL écrite dans une page.
  • Supprimer le code mort, les fichiers de test et les var_dump() oubliés.
  • Compléter le README : installation pas à pas, comptes de test.

C’est terminé quand

  • chaque ligne du tableau de sécurité du dossier indique où la règle est appliquée, et ce qui se passerait sans elle ;
  • quelqu’un d’autre, sur un autre poste, installe le projet en suivant uniquement le README, de git clone jusqu’à la connexion avec un compte de test ;
  • toutes les fonctionnalités F1 à F11 ont été vérifiées une dernière fois, sur cette installation neuve ;
  • la dernière version est sur GitHub.

Commit : « Étape 7 : relecture de sécurité et finalisation ».
