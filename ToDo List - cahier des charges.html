Projet PHP – ToDo List : cahier des charges

Présentation du projet

Vous réalisez une application web de gestion de tâches (une to-do list) en PHP, avec une base de données MySQL. Chaque utilisateur se connecte, puis gère ses propres listes de tâches.

Voici un exemple de ce qui est attendu : https://slam-sio2.alwaysdata.net/todo-list/. Pour l’essayer, connectez-vous avec le compte de test alice (mot de passe Alice2026!). Votre application peut avoir une apparence différente : ce sont les fonctionnalités et les règles de ce document qui comptent.

Le projet met en pratique les chapitres 1 à 8 du cours PHP : tableaux, fonctions, formulaires, sessions et PDO. Le nom des fichiers et l’apparence sont libres, tant qu’ils respectent les attentes de ce document.

C’est la première partie d’un projet en deux temps. Dans la partie 2, vous transformerez cette même application en architecture MVC. Un code bien rangé dès maintenant rendra ce passage beaucoup plus simple.

L’objectif est avant tout la compréhension : vous devez pouvoir expliquer le rôle de chaque fichier, le trajet d’une requête dans votre application et chacun de vos choix de sécurité.

Organisation

Le projet avance par étapes, décrites dans le guide des étapes. Chaque étape se termine par une version qui fonctionne, enregistrée avec Git.

L’usage de l’IA est autorisé pour écrire du code. Vous restez responsable de tout le code rendu : chaque ligne doit pouvoir être expliquée, modifiée et justifiée. Un code que vous ne savez pas expliquer compte comme un code que vous n’avez pas compris.

Tout au long du projet, vous remplissez un dossier de compréhension : la carte de votre application, le suivi pas à pas de deux requêtes, et le tableau des règles de sécurité appliquées.

Attentes fonctionnelles

L’application compte 11 fonctionnalités, toutes obligatoires. Une fonctionnalité est validée quand tous ses critères sont vérifiés dans le navigateur.

N° Fonctionnalité Critères de validation
F1 Inscription Un visiteur crée un compte avec un identifiant et un mot de passe. L’identifiant est unique. Le mot de passe fait au moins 8 caractères. Les erreurs s’affichent au-dessus du formulaire, et les saisies sont conservées.
F2 Connexion et déconnexion Un utilisateur se connecte avec son identifiant et son mot de passe. Un identifiant inconnu et un mot de passe faux donnent le même message. Le nom de l’utilisateur connecté apparaît sur toutes les pages. La déconnexion ramène à l’accueil.
F3 Mes listes L’utilisateur voit uniquement ses listes, avec pour chacune son nom, son nombre de tâches et son pourcentage de tâches terminées.
F4 Gérer une liste L’utilisateur crée, renomme et supprime une liste. Le nom est obligatoire. Supprimer une liste supprime aussi ses tâches.
F5 Consulter une liste La page d’une liste affiche ses tâches, avec un filtre par statut, un filtre par priorité, une recherche dans le titre et un tri (titre, échéance, date de création). Les choix restent affichés après le filtrage.
F6 Ajouter une tâche Une tâche a un titre (obligatoire), une description et une échéance (facultatives), une priorité (basse, normale ou haute) et un statut (à faire par défaut).
F7 Changer le statut d’une tâche Depuis la page d’une liste, l’utilisateur change le statut d’une tâche (à faire, en cours, terminée).
F8 Supprimer une tâche L’utilisateur supprime une tâche depuis la liste.
F9 Tableau de bord L’accueil d’un utilisateur connecté affiche : son nombre de listes, son nombre de tâches par statut, et ses 5 prochaines tâches non terminées, classées par échéance. Ces chiffres sont calculés par la base.
F10 Page introuvable Une liste ou une tâche qui n’existe pas, ou qui appartient à un autre utilisateur, affiche une page « introuvable » avec le code HTTP 404.
F11 Messages Après chaque action (ajout, changement de statut, suppression, connexion), un message confirme ce qui a été fait, ou explique l’erreur.

Attentes techniques

L’organisation du code est libre, mais elle doit respecter les points suivants. Chacun sera vérifié dans le code.

  • Une page par écran ou par action : chaque page de l’application est un fichier PHP (par exemple la page d’une liste, l’ajout d’une tâche, la suppression d’une tâche).
  • Traitement, puis affichage : chaque page commence par le traitement en PHP (vérifier la connexion, lire et vérifier les saisies, appeler les fonctions, rediriger), et se termine par l’affichage en HTML. Aucun traitement au milieu du HTML : l’affichage utilise seulement des variables préparées au-dessus, des boucles et des conditions.
  • Les requêtes SQL dans des fonctions : toutes les requêtes sont écrites dans des fonctions, regroupées dans un fichier dédié. Ces fonctions reçoivent l’objet PDO en paramètre. Aucune requête SQL n’est écrite dans une page.
  • Les autres fonctions dans un fichier de fonctions : échappement, vérification de la connexion, messages, libellés du statut et de la priorité. Aucune fonction n’est recopiée dans plusieurs pages.
  • Un démarrage commun : un fichier inclus en haut de chaque page démarre la session, désactive l’affichage des erreurs, charge les fichiers de fonctions et crée la connexion à la base.
  • Gabarit commun : l’en-tête, le menu et le pied de page sont écrits une seule fois, dans des fichiers inclus par chaque page.
  • PHP : PHP 8.2 ou plus, declare(strict_types=1) dans chaque fichier, paramètres et retours des fonctions typés.
  • PDO : une seule connexion, en mode exceptions, avec les lignes lues sous forme de tableaux associatifs.
  • Erreurs : une erreur de connexion à la base est écrite dans le journal des erreurs, et le visiteur voit seulement un message neutre. Les erreurs PHP ne sont jamais affichées.

Attentes de sécurité

Les 10 règles suivantes sont obligatoires. Dans le dossier de compréhension, vous indiquerez pour chacune où elle est appliquée dans votre code, et ce qui se passerait sans elle.

N° Règle Ce qu’elle empêche
S1 Toute valeur variable d’une requête SQL passe par un marqueur (requête préparée). L’injection SQL
S2 Toute donnée affichée qui vient de la base ou de l’utilisateur est échappée. La faille XSS
S3 Les mots de passe sont enregistrés avec password_hash() et vérifiés avec password_verify(). La lecture des mots de passe en cas de vol de la base
S4 L’identifiant de session est renouvelé à la connexion. La session ne contient jamais le mot de passe. Le vol de session
S5 Chaque page réservée vérifie elle-même la session, redirige un visiteur non connecté, et le script s’arrête après la redirection. L’accès sans compte
S6 Chaque lecture, modification ou suppression d’une liste ou d’une tâche vérifie qu’elle appartient à l’utilisateur connecté. La consultation ou la modification des données d’un autre utilisateur, en changeant un identifiant dans l’adresse
S7 Toute action qui modifie la base passe par un formulaire en POST, suivi d’une redirection. Les modifications déclenchées par un simple lien, et le double envoi par actualisation de la page
S8 Toutes les saisies sont vérifiées côté serveur : champs obligatoires, longueur du mot de passe, valeurs autorisées (statut, priorité). Les valeurs modifiées dans le navigateur (F12) ou envoyées sans formulaire
S9 Ce qui doit être fiable est décidé côté serveur : le propriétaire d’une liste vient de la session, jamais d’un champ du formulaire. L’usurpation, par un champ caché modifié
S10 Aucun détail technique (message d’erreur SQL, chemin de fichier) n’est affiché au visiteur. La fuite d’informations utiles à un attaquant

Base de données

La base compte au minimum trois tables : un utilisateur possède plusieurs listes, et une liste contient plusieurs tâches. Vous pouvez ajouter des colonnes ou des tables, à condition de les justifier. Cette base servira telle quelle dans la partie 2.

Table Colonnes minimales Règles
utilisateur id, identifiant, mdp_hash, date d’inscription identifiant unique
liste id, nom, utilisateur_id, date de création clé étrangère vers utilisateur
tache id, liste_id, titre, description, priorite, statut, echeance, date de création clé étrangère vers liste, avec suppression en cascade ; description et échéance peuvent être vides (NULL) ; priorité et statut limités à leurs valeurs autorisées

Le projet fournit un script SQL qui crée la base, puis la remplit avec des données de test : au moins 2 utilisateurs, 3 listes et 15 tâches, avec tous les statuts et toutes les priorités représentés, pour que chaque fonctionnalité puisse être essayée dès l’installation. Les mots de passe de test figurent dans le README.

Git et livrables

Le projet est versionné avec Git et déposé sur GitHub, dans un dépôt public. Son historique montre l’avancement du travail, étape par étape. Le même dépôt servira pour la partie 2.

  • Dépôt GitHub : créé dès la première étape, en public. Son lien est communiqué dès sa création.
  • Envoi régulier : le travail est envoyé sur GitHub (git push) au moins à la fin de chaque séance et à la fin de chaque étape du guide.
  • Commits : au moins un commit par étape, avec un message qui dit ce qui a été fait (« Ajout du filtre par statut », et non « modifs »).

À la fin de la partie 1, le dépôt contient :

  1. le code de l’application ;
  2. le script SQL de création et de données de test ;
  3. un fichier README.md qui explique l’installation pas à pas et donne les comptes de test ;
  4. le dossier de compréhension complété.

Le README est écrit en Markdown : un fichier texte que GitHub affiche mis en forme sur la page du dépôt. Quelques repères suffisent : # Titre pour un titre (## pour un sous-titre), - en début de ligne pour une liste, **mot** pour du gras, et les commandes entourées de trois accents graves (```) pour les afficher comme du code.
